02 · FIRST COMPLETE CUSTOMER JOURNEY

What the customer experiences, in order

This is the smallest real path that proves Onua can operate as a paid membership product.

1. Account→

The customer creates a real account and can sign in again later.

2. Price→

Onua shows the approved offer for the customer’s market.

3. Checkout→

Whop collects the digital-membership payment.

4. Confirm→

Whop sends Onua a signed message confirming what happened.

5. Record→

Onua records what this customer may watch and until when.

6. Watch→

The video provider creates a temporary protected viewing link.

7. Change→

Cancellation, refund, failed renewal, and expiry update access using the approved rules.

8. Recover→

An operator can explain a problem, retry safe work, and see every important change.

Shopify is outside this membership path. Under the proposed split, Shopify handles physical products, fulfilment, and merchandise taxes—not permission to watch Onua videos.

Regional pricing, explained honestly

The team must define which evidence determines a customer’s market. Location, billing country, payment method, and account history can disagree. Those conflicts need one written fallback rule.

No system can make location fraud impossible. The practical goal is to make obvious manipulation difficult, detectable, and reviewable without punishing legitimate travelers.

Successful test: approved markets see the correct offer; conflicting signals follow the written fallback; changing only a VPN does not silently create permanent cheaper access.

03 · BACKEND DESIGN

One understandable backend with four jobs

We need enough separation to stay safe and testable, but not a fleet of services that the team cannot operate.

Customer↓

Uses the Onua website.

Website↓

Asks the Onua backend to perform trusted actions.

Backend├

Asks Whop whether payment was real.

Backend├

Records what the customer may watch.

Backend└

Asks the video provider for a temporary viewing link.

THE FOUR JOBS

1

Know the customer

Create a real account, keep login secure, and attach payment and viewing history to one person.

2

Confirm the money

Create the Whop checkout, verify Whop’s signed payment messages, and record each money event exactly once.

3

Control viewing

Decide what the customer may watch, then create a temporary protected link instead of exposing a permanent video URL.

4

Run the service

Detect failures, alert the right person, explain customer problems, restore data, and reverse a bad release.

WHY THIS DESIGN

  • UnderstandableMatt and Vitaley can explain the complete system without tracing a maze of services.
  • SecureThe browser never holds payment secrets, signs videos, or grants itself access.
  • ReliableA repeated payment message produces one result; a temporary failure can retry safely.
  • ScalableThe CDN and video provider carry heavy media traffic. The backend makes comparatively small authorization decisions.
  • ReversibleWhop and the video provider connect through narrow boundaries, so their code does not spread through the frontend.

Not choosing now: Kubernetes, a microservice fleet, Kafka, custom video delivery, or speculative global infrastructure. We add complexity only when a measured test proves the simpler design cannot meet an accepted requirement.

Engineering principles: Keep the complete system small enough to understand. Measure real bottlenecks. Make the smallest safe improvement and prove it worked.

08 · CONTINUOUS IMPROVEMENT LOOP

Let monitoring find problems. Keep humans in control.

During this audit the loop creates local evidence packets only. Future GitHub issues or draft fixes require a separate, explicit activation record and can never silently become production changes.

1. Detect→

A proven alert notices a slow query, failed payment message, growing waiting line, access mismatch, playback delay, error spike, or cost spike.

2. Capture→

The alert attaches the affected route, time, trace, safe logs, expected threshold, customer impact, and exact deployed version.

3. Package→

Current mode: create one local evidence packet with severity, reproduction, acceptance test, owner, and rollback boundary.

4. Propose→

Only after activation: create the authorized issue and, for a named narrow pattern, a separate branch and draft pull request.

5. Prove→

Machine tests reproduce the failure, prove the fix, and run the relevant security, correctness, load, and regression checks.

6. Review→

An independent reviewer checks the full workflow, not only the changed lines.

7. Decide→

Matt reviews architecture and evidence. Vitaley provides any required merge authorization.

8. Release→

Deployment remains a separate explicit decision with immediate smoke proof and rollback.

Why this helps Onua

Faster learning

Real bottlenecks arrive with evidence instead of becoming vague complaints.

Less firefighting

Repeated problems gain a tested response and a named owner.

Safer scale

The team improves what measurements show instead of building speculative infrastructure.

Durable memory

Every failure becomes a regression test, runbook step, or tracked decision.

Automate only the narrow, proven patterns

Good early candidatesKeep human-led
Known missing index or reproduced slow-query regressionPayment semantics or viewing-access policy
Repeated unnecessary API or database callsAuthentication and authorization design
Known non-payment connection-reuse regressionPayment/authentication timeout, retry, or ordering behavior
Regression already protected by a deterministic testRegional pricing, refunds, cancellation, vendor, or architecture changes

ACTIVATION RULE

Correct → measure → alert → automate

Do not automate a path that has not passed end to end. Future activation must name the exact repository, writable paths, issue/branch/draft-PR permissions, credential scope, allowed failure patterns, rate limit, owner, audit log, current-head review rule, and kill switch.

Until that activation is explicitly approved, the loop stops at a local evidence packet: no GitHub issue, branch, commit, pull request, merge, or deployment.

09 · OPTIONAL ENGINEERING DETAIL

The technical parts behind the four plain-English jobs

This section helps the builders. Vitaley does not need to memorize it to understand the plan.

1. Account and login
What

Creates users and secure sessions.

Why

Money and viewing rights need one stable person.

Successful test

A user signs in again later and cannot access another user’s records.

2. Market and price decision
What

Selects an approved market, currency, and offer using server rules.

Why

The browser must not choose its own price.

Successful test

Correct offers appear and conflicting evidence follows the written fallback.

3. Whop connection
What

Creates or selects the approved membership checkout.

Why

Whop-specific behavior stays in one replaceable place.

Successful test

Browser tampering cannot change the plan or amount.

4. Secure payment-message receiver (webhook)
What

Verifies and stores Whop’s signed message.

Why

A checkout success screen is not proof of payment.

Successful test

Valid messages store, forged messages fail, and repeated delivery is safe.

5. Payment history and retry worker
What

Records money changes and retries temporary failures.

Why

Every money decision must be explainable and recoverable.

Successful test

A forced outage alerts, waits, and later completes the event once.

6. Viewing-access record (entitlement)
What

Records whether the customer may watch and until when.

Why

Payment status and viewing policy are not always identical.

Successful test

Paid, canceled, expired, refunded, and renewal-failed examples match policy.

7. Database and access rules
What

Stores users, events, payments, access, and history.

Why

One durable record prevents competing versions of truth.

Successful test

Concurrent events remain consistent and users see only their own records.

8. Protected playback
What

Creates a short-lived video link after checking access.

Why

A permanent public URL defeats paid membership.

Successful test

Paid viewing works; logged-out, unpaid, expired, and copied-link paths fail safely.

9. Security and monitoring
What

Adds limits, logs, measurements, traces, and alerts.

Why

The team needs to detect abuse and locate failures.

Successful test

One test customer traces end to end and thresholds alert a named operator.

10. Operator view and recovery
What

Shows account, payment, and access state with narrow recovery actions.

Why

Support cannot solve launch incidents from raw database tables.

Successful test

An operator explains a denial, safely retries work, and leaves an audit record.

Plain-English glossary

Webhook
Whop sends our backend a signed message saying a payment event occurred.
Idempotency
If Whop sends the same message twice, access changes once.
Entitlement
The database record saying what a customer may watch and until when.
Signed video link
A temporary viewing link that cannot be shared publicly forever.
Queue
A controlled waiting line that protects the backend during a burst.

How work moves

One outcome

One issue, one feature branch, and one early draft pull request.

No direct main

Vitaley separately authorizes merge and deployment. One does not imply the other.

One contract

Frontend and backend use the same versioned requests, responses, account states, errors, and realistic test examples.

Generated files

Tiardt changes authoritative generator inputs. Durable manual edits to generated output are rejected.

Durable truth

Repository, issues, pull requests, decisions, tests, and verified runtime—not giant prompts or direct messages.

Stop immediately if: work no longer matches the approved customer journey; generated output is edited directly; two systems claim the same truth; cost or vendor lock-in changes materially; scope grows without a tradeoff; component tests replace the real customer path; or an owner decision is being made implicitly.
